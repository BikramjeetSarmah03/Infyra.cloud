# AWS — Provider Integration

S3 (storage) and adjacent services. Listed in [product.md](../product.md) §4 as **designed for, not yet built**, and in §5 as one of the "future partner-program providers" the interface must structurally accommodate.

This doc establishes the `cloud_role` auth type described in [README.md](./README.md#the-fourth-authtype). AWS is the canonical case: the cross-account IAM role pattern is a documented, first-class AWS mechanism for exactly this scenario, not a workaround.

## 1. At a Glance

| | |
|---|---|
| **Base URL** | Per-service, per-region: `https://s3.{region}.amazonaws.com`, `https://sts.amazonaws.com` |
| **Auth type** | `cloud_role` — STS `AssumeRole` with `ExternalId` |
| **Category** | `storage` (S3 first; compute later) |
| **Adapter interface** | `StorageAdapter extends ProviderAdapter` — new category, see §6.1 |
| **Auth mechanism** | SigV4 request signing with temporary credentials |
| **Credential TTL** | **15 min – 12 h** (role's `MaxSessionDuration`); default 1 h |
| **Partner approval needed** | No — but customer-side setup is required |

## 2. Authentication — Cross-Account `AssumeRole`

**infyra must never ask an agency for AWS access keys.** Long-lived IAM user keys are the credential AWS explicitly steers third parties away from. The correct pattern — the one AWS documents for SaaS accessing a customer account — is a customer-created IAM role that infyra assumes.

### 2.1 The trust relationship

Three pieces of information flow between infyra and the customer:

| Direction | Item | Notes |
|---|---|---|
| infyra → customer | infyra's AWS account ID | The `Principal` in their trust policy |
| infyra → customer | A unique `ExternalId` per connection | **Generated by infyra**, never by the customer |
| customer → infyra | The created role's ARN | Stored on the connection |

The customer creates a role whose trust policy is:

```jsonc
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "<INFYRA_AWS_ACCOUNT_ID>" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": { "sts:ExternalId": "<ExternalId infyra generated for this workspace>" }
    }
  }]
}
```

…plus a permission policy scoped to what §4 actually needs.

### 2.2 `ExternalId` — the rules that actually matter

The external ID exists to prevent the **confused deputy problem**: without it, if infyra can be tricked into assuming a role ARN it was given by attacker A, and that ARN belongs to victim B who also uses infyra, infyra becomes a deputy acting on A's behalf against B's account.

Non-negotiable rules, straight from AWS's guidance:

1. **infyra generates it, not the customer.** A customer-chosen value can collide with another customer's, which defeats the purpose. Generate one random value per AWS-account connection.
2. **It is not a secret.** AWS states this explicitly — anyone who can view the role can see it. So it must not be treated as a credential, must not be the only thing protecting anything, and its presence in the encrypted blob is for uniformity, not confidentiality.
3. **One per customer AWS account**, not one global infyra value. A shared external ID across all customers provides no isolation whatsoever.
4. **Verify the role cannot be assumed without it.** AWS's guidance is explicit and should be built into the connect flow: at connect time, attempt `AssumeRole` **both with and without** the external ID. If the no-external-id attempt succeeds, the customer's trust policy is misconfigured — **refuse to store the connection** and tell them to fix it.

Rule 4 is the one most implementations skip. It turns infyra from a service that hopes customers configured trust correctly into one that verifies it, and it costs one extra API call at connect time.

Format constraints: 2–1224 characters, alphanumeric plus `+=,.@:/-`, no whitespace. A UUID satisfies this.

### 2.3 `assumeCredential(connection)`

```
POST https://sts.amazonaws.com/
Action=AssumeRole
&Version=2011-06-15
&RoleArn=<stored role ARN>
&RoleSessionName=infyra-<workspace_id>-<short request id>
&ExternalId=<stored external id>
&DurationSeconds=3600
```

Returns `AccessKeyId`, `SecretAccessKey`, `SessionToken`, `Expiration`.

**`RoleSessionName` lands in the customer's CloudTrail.** Make it identify the workspace and correlate to an infyra request ID — the customer's auditor should be able to trace any infyra-initiated action back to a specific workspace and operation. This is a compliance feature the agency's own clients may eventually require, and it costs nothing to get right at the start.

### 2.4 `getTrustConfig(workspaceId)`

The connect UI needs to render setup instructions. This method returns infyra's account ID, the generated external ID, the required permission policy JSON, and ideally a one-click CloudFormation/Terraform template. Hand-writing IAM policies is where customers give up or over-grant `AdministratorAccess` — a template is the difference between a working integration and an insecure one.

## 3. Credential Lifetime

| | |
|---|---|
| Minimum | 15 minutes |
| Default | 1 hour |
| Maximum | 12 hours (role's `MaxSessionDuration`, customer-controlled) |
| Refresh flow | **None** — mint a new one via `AssumeRole` |

This inverts the storage model of every other provider:

| | Neon/Supabase | Render/Cloudflare | **AWS** |
|---|---|---|---|
| What's stored | Refresh token (secret) | API key (secret) | **Role ARN + external ID (not secret)** |
| What's used per call | Access token | The stored key | **Freshly minted temp credentials** |
| If the DB leaks | Attacker acts as the user | Attacker acts as the user | **Attacker gets nothing usable** |

That last column is the security payoff and the reason `cloud_role` deserves to be its own auth type rather than being forced into `api_key`. The encrypted blob holds no secret at all — an attacker with the database and the encryption key still cannot assume the role, because they aren't infyra's AWS account.

**Never cache temporary credentials beyond their `Expiration`, and never persist them.** They live in the request/job scope only, per [adapter-design.md](../adapter-design.md) §3.2. Caching in-memory for the life of a job is fine and desirable (avoid an `AssumeRole` per S3 call); writing them to the database is not.

### `checkHealth()`

`AssumeRole` succeeding *is* the health check.

| Outcome | Status |
|---|---|
| Success | `connected` |
| `AccessDenied` | `revoked` — role deleted or trust policy changed |
| `InvalidClientTokenId` | `invalid` — infyra-side credential problem; alert internally |
| Throttling / 5xx | No status change |

## 4. Core Endpoints → Adapter Methods

AWS uses per-service APIs with SigV4 signing rather than one REST surface. **Use the AWS SDK inside the adapter** — hand-rolling SigV4 is a correctness risk with no upside. This does not violate [adapter-design.md](../adapter-design.md) §7's "no provider SDK outside the adapter" rule; it's exactly what that rule permits.

### 4.1 STS

| Adapter method | Action |
|---|---|
| `assumeCredential()` | `sts:AssumeRole` |
| — identity check | `sts:GetCallerIdentity` |

### 4.2 S3 (`StorageAdapter`)

| Adapter method | Action |
|---|---|
| `listResources()` | `s3:ListAllMyBuckets` |
| `createResource()` | `s3:CreateBucket` |
| `deleteResource()` | `s3:DeleteBucket` |
| — bucket region | `s3:GetBucketLocation` |
| — policy/CORS | `s3:PutBucketPolicy`, `s3:PutBucketCors` |
| `getUsage()` | CloudWatch `GetMetricStatistics` — see §6.3 |

### 4.3 Minimum permission policy

```jsonc
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "s3:ListAllMyBuckets", "s3:GetBucketLocation",
      "s3:CreateBucket", "s3:DeleteBucket",
      "s3:PutBucketPolicy", "s3:PutBucketCors"
    ],
    "Resource": "*"
  }, {
    "Effect": "Allow",
    "Action": ["cloudwatch:GetMetricStatistics"],
    "Resource": "*"
  }]
}
```

Note there are **no object-level permissions** (`s3:GetObject`, `s3:PutObject`). infyra provisions and manages buckets; it does not read customers' data. Keeping object access out of the policy is a meaningful trust statement to an agency handing over access to their AWS account, and it should stay out unless a concrete feature requires it.

### 4.4 Normalizing into `resources`

| `resources` column | AWS source |
|---|---|
| `provider_resource_id` | Bucket name (globally unique across all of AWS) |
| `type` | `object_storage` |
| `status` | Derived — S3 buckets have no status field; existence = `active` |
| `metadata` | `{ region, creationDate, versioning, publicAccessBlock }` |

## 5. Rate Limits & Errors

Per-service and generally high for control-plane calls; S3 bucket operations (create/delete) are the constrained ones. AWS SDKs implement adaptive retry with jitter by default — **keep it on** rather than layering custom retry logic, per [adapter-design.md](../adapter-design.md) §7's rule that retry policy belongs inside the adapter.

| AWS error | Normalized error |
|---|---|
| `AccessDenied`, `ExpiredToken` | `AdapterAuthError` |
| `NoSuchBucket`, `NoSuchKey` | `AdapterNotFoundError` |
| `InvalidBucketName`, `BucketAlreadyExists` | `AdapterValidationError` |
| `Throttling`, `SlowDown`, `RequestLimitExceeded` | `AdapterRateLimitError` |
| 5xx, `ServiceUnavailable` | `AdapterUnknownError` |

## 6. Adapter Notes

### 6.1 `StorageAdapter` is a new category interface
S3 fits neither `DatabaseAdapter` nor `DeployAdapter`. Per [adapter-design.md](../adapter-design.md) §1.3, this is the designed-for case: add a third category extension rather than bolting bucket methods onto the base.

```
StorageAdapter extends ProviderAdapter
├── createBucket(credential, spec)
├── listBuckets(credential)
├── deleteBucket(credential, bucketId)
├── getBucketPolicy(credential, bucketId)
└── setBucketPolicy(credential, bucketId, policy)
```

Cloudflare R2 and Cloudinary ([product.md](../product.md) §4) implement the same interface — so define it when the *second* storage provider is built, using both to check the abstraction, rather than shaping it around S3 alone.

### 6.2 `cloud_role` adds two methods to the base interface
`getTrustConfig()` and `assumeCredential()` — see [README.md](./README.md#the-fourth-authtype). Both throw `NotSupportedError` on `oauth`/`api_key` adapters, consistent with how `getAuthUrl()` and `validateApiKey()` already work in [adapter-design.md](../adapter-design.md) §2. **This means `cloud_role` requires no structural change to the interface**, only a third group of auth-type-specific methods — which is what [product.md](../product.md) §5 claimed would be true, now verified against a real provider's requirements.

### 6.3 Usage/billing data is genuinely hard here
Unlike Neon's `consumption_history` or Supabase's `usage` endpoints, AWS has no simple per-resource cost API. Options are Cost Explorer (`ce:GetCostAndUsage` — costs money per call, ~24h lag) or CloudWatch metrics (storage bytes, request counts — not dollars).

For [product.md](../product.md) §7's per-client cost tracking with agency markup, **CloudWatch metrics plus infyra-side pricing calculation is the tractable path**; Cost Explorer's lag and per-request cost make it unsuitable for a dashboard. Flag this as a real gap: AWS cost attribution is a project in itself, not an adapter method, and it should not be scoped as "just implement `getUsage()`."

### 6.4 Bucket names are globally unique across all AWS customers
Not per-account — globally. A deterministic name like `infyra-<workspace>-<project>` can collide with a bucket owned by a stranger, returning `BucketAlreadyExists` for a name the customer has never used. Include a random suffix and store the actual name as `provider_resource_id`. This breaks the name-based idempotency pre-check used for every other provider — but AWS supports real idempotency tokens (`ClientToken`) on most create calls, so use those instead.

### 6.5 Region is explicit and non-inferable
Every S3 call is region-scoped, and there's no sensible default. This connects to [architecture.md](../architecture.md) open question #3: for AWS, region must be captured **per connection or per resource**, and cannot be derived from a workspace-level preference alone, because one AWS account routinely spans regions.
